# 🧩 SPLIT-ADAPT-SPEC — ТЗ на адаптацию split-home.sh к текущей разметке

Версия: 1.1 от 2026-09-03. Источник: сверка констант split-home.sh с фактической
разметкой /dev/nvme0n1. Правила общие: `set -Eeuo pipefail` сохраняется,
`bash -n` / `shellcheck -S warning` = 0, `make test-fast` и `sudo -n make test`
зелёные, один коммит = одна задача (формат `A1: ...`).

Контекст: разметка диска изменилась ПОСЛЕ закрытия SPLIT-SPEC — p7 кто-то уже
сжал с 627 до 528 ГБ и в конце диска создал p8 (exfat, метка `Distr`, 99 ГБ,
дистрибутивы/образы; на нём `$RECYCLE.BIN` — раздел монтировался и из Windows).
Перенос /home при этом НЕ выполнялся: /home по-прежнему на p7 (занято 118 ГБ).
Итог: split-home.sh сейчас падает даже в `--dry-run` на защите «p8 уже
существует», а его геометрия (`mkpart ... 100%`, «~427 ГБ») разошлась с диском.

Фактическая разметка (sfdisk -d, 2026-09-03), фундамент для констант:

| Раздел | start (секторов) | size (секторов) | Размер | Что это |
|---|---|---|---|---|
| p7 | 638709760 | 1107075072 | 527.9 GiB | ext4 `/`, UUID `1b8e3e50-2e22-4088-a3a5-396293780ff2` — не изменился |
| p8 | 1745784832 | 207738880 | 99.1 GiB | exfat `Distr`, PARTUUID `58c56411-3703-410a-bda7-41278b287bca` |
| — | 1058140160 | 687644672 | 328.0 GiB | свободный диапазон после сжатия p7 до 200 GiB — место нового p9 |

Ключевая арифметика: конец p7 при 200 GiB = 638709760 + 419430400 − 1 =
1058140159 (совпадает с прежним); диапазон нового раздела = 1058140160 ..
1745784831 (конец = старт Distr − 1). Граница 200 GiB и логика сжатия
(195G → resizepart → resize2fs) не меняются.

## A1 (S) 🔴 Константы разметки и отпечаток p8-Distr

Скрипт остаётся привязанным к железу — меняем ожидания, а не убираем проверки.

1. Переименовать целевой раздел: `P8=…` → **`P9="${DISK}p9"`** (новый /home);
   завести `P8_DISTR="${DISK}p8"` для проверок существующего раздела.
2. Новые константы-отпечатки рядом с `EXPECT_P7_UUID`:
   `EXPECT_P7_SIZE_SECTORS=1107075072` (p7 уже сжат до 528 ГБ),
   `EXPECT_DISTR_START=1745784832`, `EXPECT_DISTR_PARTUUID=58c56411-3703-410a-bda7-41278b287bca`.
3. В `check_environment` заменить die «p8 уже существует» на тройную проверку:
   - p9 существует → die «операция уже выполнялась?»;
   - p8 НЕ существует → die «разметка не соответствует: нет раздела Distr»;
   - p8 не совпадает с отпечатком (blkid TYPE=exfat + PARTUUID из
     `/sys/block/nvme0n1/nvme0n1p8/start` и lsblk PARTUUID; существующая
     проверка старта p7 — образец) → die «разметка изменилась, обновите
     константы в скрипте»;
   - добавить сверку `Z7 == EXPECT_P7_SIZE_SECTORS` (существующий `S7`-чек —
     образец): p7 уже сжат или расширен → die.
4. Все проверки — ДО первого `run parted`/`mkfs` (порядок в коде сохранить).

Приёмка: код; на этой машине до правок `sudo bash split-home.sh --dry-run`
падает с «Раздел /dev/nvme0n1p8 уже существует» (вывод зафиксировать как
«красный» эталон в итоговом сообщении), после — доходит до конца.

## A2 (S) 🔴 Геометрия p9: mkpart с явным концом вместо 100%

1. `P9_START_SECTOR` = прежняя формула `P7_END_SECTOR + 1` (= 1058140160);
   добавить `P9_END_SECTOR=$((EXPECT_DISTR_START - 1))` (= 1745784831).
2. `parted -s "$DISK" mkpart "UbuntuHome" ext4 "${P9_START_SECTOR}s" "${P9_END_SECTOR}s"`
   — конец явный, `100%` запрещён (сейчас перекрыл бы Distr).
3. `mkfs.ext4 -F -L "UbuntuHome" "$P9"`.
4. В `do_migrate_home` монтировать и форматировать `P9`, UUID для fstab брать
   с `P9` (механика S1–S5 — без изменений, только имя раздела).
5. Инфо-строка «Целевой размер p9: ~N ГБ» остаётся динамической
   (`Z7 − P7_SIZE_SECTORS` даёт ровно 328 — формула корректна и после правок).

Приёмка: в dry-run выводе `mkpart ... 1058140160s 1745784831s` и
`mkfs.ext4 ... /dev/nvme0n1p9`; упоминаний `p8` как цели /home в коде нет
(`grep -n 'P8' split-home.sh` — только P8_DISTR).

## A6 (S) 🔴 parted: подтверждение сжатия resizepart (латентный баг)

Обнаружено при проверке на loop-образе (parted 3.4): `parted -s resizepart`
при СЖАТИИ раздела печатает «Warning: Shrinking a partition can cause data
loss» и обрывается с rc≠0 — флаг `-s` подтверждение сжатия НЕ подавляет.
Значит, текущая строка `run parted -s "$DISK" resizepart 7 "${P7_END_SECTOR}s"`
упадёт на реальном прогоне в шаге 5 (уже после долгого e2fsck/resize2fs), и до
создания p9 дело не дойдёт. `mkpart` подтверждения не требует — его править не
нужно.

Решение: подать «Yes» на stdin через `---pretend-input-tty`:
`run parted ---pretend-input-tty "$DISK" resizepart 7 "${P7_END_SECTOR}s" <<< "Yes"`.
Проверено: rc=0, раздел сжимается до заданного сектора. В dry-run вывод честно
отражает команду с флагом и herestring.

Приёмка: `bash -n`/shellcheck 0; проверка на loop-образе (shrink без интерактива,
rc=0) — вручную либо сценарием в `make test-loop`; golden регенерирован, в diff —
ровно изменённая строка resizepart.

## Загрузка после разделения — инварианты и проверка

Цепочка UEFI: прошивка → ESP (p1) → GRUB → ядро + initramfs из /boot (p7) →
`root=UUID=1b8e3e50-…` → initramfs монтирует `/` (p7), затем systemd монтирует
`/home` по новой строке fstab (`UUID=<p9>`); swap (p6) возвращается по старой
строке fstab (скрипт выполнял `swapoff -a`).

Почему загрузка не ломается: `resize2fs` и `parted resizepart` не меняют ни UUID
файловой системы p7, ни его стартовый сектор; /boot остаётся на месте. GRUB и
initramfs адресуют разделы по UUID, а не по номеру, поэтому:
- `grub-install` / `update-grub` НЕ требуются;
- Windows Boot Manager (p1–p5) не затрагивается.

Нюанс нумерации (проверено parted 3.4): новый раздел получит НОМЕР p9, но
физически встанет МЕЖДУ p7 и p8 — итоговый порядок p7 → p9 → p8. Это
непривычно, но безвредно (адресация по UUID); существующий p8-Distr не
перенумеровывается.

Проверки после перезагрузки (расширяют ШАГ 6 в шапке скрипта):
- `df -hT / /home` — `/` на p7 (200 ГБ), `/home` на p9 (~328 ГБ);
- `lsblk` — появился `nvme0n1p9` (стоит между p7 и p8);
- `cat /etc/fstab` — строка `/home` с UUID p9;
- `swapon --show` — swap на p6 вернулся;
- `lsblk -o NAME,LABEL,SIZE` — `Distr` на месте и монтируется.

## Явно НЕ входит

- Удаление, переформатирование или перемещение p8-Distr — раздел сохраняется
  как есть со всеми данными; место под p9 берётся только из свободного gap'а.
- Изменение целевой границы 200 GiB и параметров сжатия (195G, 200 GiB),
  стартового сектора p7 `638709760`, UUID p7, `USED_LIMIT_GB=190`,
  `TARGET_SHRINK_GB=195` (A6 границу не меняет — только убирает подтверждение).
  Номер и конечный сектор нового раздела (p9, `1745784831s`) и новые отпечатки
  текущей разметки (`EXPECT_P7_SIZE_SECTORS`, Distr) — НЕ из этого пункта:
  это и есть суть A1/A2.
- Пересмотр порядка миграции и сверки из SPLIT-SPEC (S1–S5 закрыты и приняты).
- Генерализация под другие машины (скрипт остаётся личным, привязанным к железу).
- Любая правка deploy.sh, make-boot-usb.*, templates/, autounattend.
