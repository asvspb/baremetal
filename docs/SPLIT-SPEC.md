# 🧩 SPLIT-SPEC — ТЗ на доработку split-home.sh

Версия: 1.0 от 2026-09-02. Источник: детальное изучение split-home.sh после
завершения FIX-SPEC. Все задачи — bash, правила общие: `set -Eeuo pipefail`
сохраняется, `bash -n`/`shellcheck -S warning` = 0, `make test-fast` и
`sudo -n make test` зелёные, один коммит = одна задача (формат `S1: ...`).

Контекст: split-home.sh — одноразовая операция на целевом NVMe (сжатие p7 до
200 GiB + перенос /home на новый p8). Скрипт спроектирован правильно (порядок
сжатия канонический, идентификация цели по UUID/сектору/типу), но миграция
данных в §7 имеет два слабых места, найденных разбором: удаление старого /home
идёт ДО обновления fstab (опасное окно при прерывании), и копия не сверяется
перед уничтожением оригинала. Оба противоречат стандарту проекта «сверка до
удаления» (verify_restored_tree / Test-BackupTreeMatch с критическими тестами).

---

## S0 (M) 🔴 Guard-рефакторинг + золотой эталон dry-run

Раньше split-home.sh сознательно не рефакторился. Теперь это необходимо:
критические сценарии S1/S2 иначе не покрыть автотестами. Рефакторинг строго
поведение-сохраняющий:

1. **ДО правок** зафиксировать эталон на этой машине (диск-цель здесь присутствует,
   S-H3 проходит): `sudo bash split-home.sh --dry-run > tests/fixtures/split-home-dry.golden`.
2. Весь верхнеуровневый код (всё после объявлений функций) обернуть в
   `main() { ... }` + guard `if [[ "${BASH_SOURCE[0]}" == "$0" ]]; then main "$@"; fi`
   — по образцу deploy.sh (T0 прошлых этапов). Логику не переносить и не
   переименовывать, только обернуть.
3. Блок миграции §7 (mount → rsync → fstab → очистка → umount) оформить функцией
   `do_migrate_home()` без изменения поведения; точки монтирования, TS и пр.
   остаются глобальными переменными.
4. Сравнить вывод dry-run с эталоном — **побайтово идентичен**, иначе S0 не принят.

Приёмка: golden до/после идентичен; `bash -n`, shellcheck 0; существующие
S-H1..S-H3 зелёные.

## S1 (S) 🔴 fstab — ДО удаления старого /home

**Проблема.** Сейчас: rsync → `find -delete` (старый /home уничтожен) → fstab.
Прерывание между ними (Ctrl-C, питание — ловушек нет) = перезагрузка в систему
с пустым /home и данными на невмонтированном p8.

**Решение.** Новый порядок внутри `do_migrate_home()`:
1. rsync -aHAXS (см. S4 про -S) + сверка (S2);
2. бэкап fstab (`fstab.bak-$TS`), дописывание строки `UUID=... /home ext4 defaults 0 2`,
   копирование parttable-бэка в `/root` целевой системы — всё как сейчас;
3. только после успешного fstab — `find "$MNT_ROOT/home" -mindepth 1 -delete`.
4. В финальный вывод добавить строку-подсказку: при прерывании между fstab и
   очисткой старые файлы остаются на p7 под точкой монтирования; чистка:
   Live → mount p7 → `rm -rf /mnt/p7/home/*` (безопасно, p8 уже /home).

Прерывание теперь оставляет максимум «незачищенные старые копии», а не пустой home.

Приёмка: порядок в коде; dry-run вывод отражает новый порядок; сценарные тесты
S5 (fstab при сбое сверки не пишется; при успехе — пишется и старый /home пуст).

## S2 (S) 🔴 Сверка копии до удаления оригинала

**Решение.** После rsync, до любых изменений fstab/удаления:

```bash
verify_out="$(rsync -aHAXSn --itemize --out-format='%i %n' \
    "$MNT_ROOT/home/" "$MNT_HOME/" 2>&1 || true)"
if [[ -n "$verify_out" ]]; then
    die "Сверка /home после копирования не сошлась (первые расхождения):
$verify_out
Старый /home НЕ удалён, fstab НЕ изменён. Разберитесь с расхождениями вручную."
fi
```

Второй проход в dry-режиме rsync (`-n`) с itemize: пустой вывод = деревья
идентичны (содержимое, права, xattr, ACL, жёсткие ссылки). Непустой = die ДО
уничтожения оригинала. Это тот же стандарт, что I-M4 в make-boot-usb.sh.

Приёмка: код; dry-run упоминает сверку; сценарный тест S5: инъекция расхождения
(режим rsync-заглушки `STUB_RSYNC_DIFF`) → die, старый /home цел, fstab без /home.

## S3 (S) 🟡 Ранняя проверка занятого места

**Проблема.** Сейчас о слишком заполненном /home (суммарно > ~194 ГБ) узнаём
только по отказу `resize2fs 195G` — после долгого e2fsck. Fail-safe, но поздно.

**Решение.** После блока §1 (UUID подтверждён), до GPT-бэка:
примонтировать p7 в ro-каталог `/tmp/split_preflight`, снять
`df -B1G --output=used`, отмонтировать; если занято ≥ 190 ГБ — die с понятным
сообщением (порекомендовать освободить /home). В dry-run — только вывести
цифру инфо-строкой. Порог оформить переменными `TARGET_SHRINK_GB=195` /
`USED_LIMIT_GB=190` рядом с константами разделов.

Приёмка: die при переполнении (юнит-сценарий с заглушкой df/mount), инфо-строка
в dry-run; golden ПЕРЕГЕНЕРИРОВАН, в diff — ровно одна добавленная строка
(занято N ГБ), ревью diff в коммите.

## S4 (S) 🟢 Мелочи надёжности

1. `cleanup`-ловушка на EXIT/INT/TERM: отмонтировать `$MNT_HOME`, `$MNT_ROOT`,
   если смонтированы (по `/proc/mounts`), с `|| true` и `return 0` — по образцу
   `cleanup_mounts` в deploy.sh. Определить после объявления MNT-переменных,
   с защитой от пустых значений.
2. `rsync -S` (sparse-файлы, образы ВМ) — добавить в ОБА прохода: копирование и
   сверку (флаги должны совпадать, иначе сверка даст ложные расхождения).
3. После монтирования p8 — `fstrim -v "$MNT_HOME" 2>/dev/null || true`
   (через `run`, чтобы dry-run честно показывал).

Приёмка: прерывание по Ctrl-C посреди rsync не оставляет монтирований (ручная
проверка в Live — пункт чек-листа); флаги rsync в обоих проходах идентичны;
shellcheck 0.

## S5 (M) 🟢 Сценарные тесты критических путей

На базе S0 (source + guard) и существующего паттерна `tests/bats/scenarios/`
(образец — m3/m5): tmp-каталоги как MNT_ROOT/MNT_HOME с фальшивым деревом /home
и `etc/fstab`, заглушка blkid для UUID p8, расширение rsync-заглушки режимом
`STUB_RSYNC_DIFF` (в `-n`-проходе эмитит строку расхождения).

Обязательные тесты (аналог «критических» I-M3/I-M4):
- сбой сверки → die, старый /home НЕ тронут, fstab БЕЗ записи /home;
- успех → fstab содержит UUID p8, старый /home пуст, порядок операций верен;
- сбой rsync (существующий режим заглушки) → die до сверки и fstab.

Приёмка: 3 новых теста зелёные в `make test-fast`; острая проверка: временная
порча сверочного кода (убрать die) обязана краснить тест №1 — результат
зафиксировать в итоговом сообщении (как делалось для I-M3/I-M4).

## Явно НЕ входит

- Изменение секторной арифметики, размеров 200/427 ГБ, UUID-констант — запрещено.
- Генерализация под другие машины/параметры (скрипт остаётся личным, привязанным к железу).
- LUKS/шифрование, btrfs, изменение fstab-опций монтирования /home.
- Любая правка deploy.sh, make-boot-usb.*, templates/ — вне рамок.
- Пересмотр уже принятых решений FIX-SPEC.
