# 🔧 FIX-SPEC — ТЗ на оставшиеся доработки («хвост»)

Версия: 1.0 от 2026-09-02. Источник: разбор реального лога запуска
make-boot-usb.ps1 v2026-09-02.2 на Windows 11 / PS 5.1 (Kingston DataTraveler 8GB)
и обсуждение индикатора копирования.

Общие правила (обязательны): правки `.ps1` — байт-безопасно, UTF-8 BOM + CRLF,
проверки `check-files.sh` + парс pwsh; при правке `make-boot-usb.ps1` — bump
`$ScriptVersion` (формат `ГГГГ-ММ-ДД.N`); один коммит = одна задача; `bash -n`,
`shellcheck -S warning` = 0; `make test-fast` зелёный.

## T1 (S) 🔴 Убрать WARN `Set-Partition -Attributes` (make-boot-usb.ps1)

**Проблема.** В блоке сокрытия VTOYEFI вызов
`Set-Partition ... -GptType '{c12a7328-...}' -Attributes 0xC000000000000001`
падает на привязке параметров: в Storage-модуле Windows PowerShell 5.1 параметра
`-Attributes` нет. Ошибка уходит в catch → WARN в каждом запуске; при этом
cmdlet не применяет и `-GptType` (привязка ломается до выполнения). Атрибуты и
GUID в итоге ставит diskpart-фолбэк (шаг 5) — поэтому итог верный, но WARN шумит
и маскирует настоящие предупреждения.

**Решение.** Разделить вызов:
1. `Set-Partition -DiskNumber ... -PartitionNumber 2 -GptType '{c12a7328-f81f-11d2-ba4b-00a0c93ec93b}'` — оставить (в 5.1 поддерживается).
2. `-Attributes 0xC000000000000001` — убрать из cmdlet-вызова полностью; за
   атрибуты отвечает diskpart (`gpt attributes=0xC000000000000001`), он уже есть
   и успешно отрабатывает.

**Приёмка.** В логе следующего реального запуска нет WARN про `Attributes`;
шаг diskpart по-прежнему SUCCESS; pwsh-парс OK; версия bumped. Задача
статически не тестируется (Storage-модуль есть только на Windows) — приёмка по
логу + ревью.

## T2 (S) 🟡 Честный замер чтения (make-boot-usb.ps1, Run-SpeedTest)

**Проблема.** Тест чтения читает файл, только что записанный самим тестом, —
Windows отдаёт его из кэша ОС. В реальном логе: «Чтение = 4089 МБ/с» на флешке
с записью 4,9 МБ/с. Число вводит в заблуждение. (В bash-версии проблемы нет —
там делается `echo 3 > /proc/sys/vm/drop_caches`.)

**Решение — вариант A (принят, минимальный).**
1. Метку «Чтение» заменить на «Чтение (из кэша ОС)» в консоли и логе.
2. В README (раздел про замеры, если нет — добавить примечание к «Тестирование»)
   зафиксировать: чтение измеряется из кэша и отражает производительность
   конвейера ОС, а не флешки; скорость записи — честная.

Вариант B (отложен, не делать без отдельного решения): чтение через
`FileStream` с флагом `FILE_FLAG_NO_BUFFERING` (0x20000000) по выровненному
буферу 1 МБ — честный холодный замер, но требует аккуратной работы с
выравниванием и рискует ошибками на некоторых носителях.

**Приёмка.** Вывод и лог содержат пометку «(из кэша ОС)»; pwsh-парс OK;
README дополнен; версия bumped.

## T3 (S/M) 🟡 Длительности этапов в лог (make-boot-usb.ps1)

**Проблема.** Пауза машины во сне (31 мин в реальном логе) видна только как
разрыв таймстемпов между записями — неудобно при разборе. Хочется явные
«этап занял N сек».

**Решение.** Добавить helper и обернуть ключевые фазы:

```powershell
function Measure-Phase {
    param([string]$Name, [scriptblock]$Body)
    $sw = [System.Diagnostics.Stopwatch]::StartNew()
    & $Body
    Write-Log ("Этап '{0}' завершен за {1} сек" -f $Name, [int]$sw.Elapsed.TotalSeconds) "INFO"
}
```

Обернуть фазы (не менять их код, только вызов): проверка целостности, бэкап
(общее время), установка Ventoy, скачивание/установка темы, восстановление ISO,
восстановление данных, замеры скорости (оба). Пауза ОС внутри фазы сразу видна
как аномальная длительность.

**Приёмка.** В логе ≥ 7 строк «Этап '...' завершен за N сек»; пауза сна
локализуется в конкретный этап; pwsh-парс OK; версия bumped.

## T4 (M) 🟢 Прогресс восстановления в Linux-версии (make-boot-usb.sh)

**Проблема.** `restore_files()` копирует молча: `cp -a` без индикатора. Бэкап
уже показывает прогресс (`rsync --info=progress2`), восстановление — нет.
Асимметрия с ps1-версией, где теперь есть `Copy-WithProgress`.

**Решение.** В `restore_files()` заменить два `cp -a "$BACKUP_DIR/..." "$mnt/"`
на `rsync -a --info=progress2 ...` (тот же инструмент, что в бэкапе; даёт
процент, скорость и ETA). Проверить тесты: сценарии I-M5/`m5-success-cycle`
используют реальные cp/rsync в среде стабов — при необходимости поправить
ожидания сценариев; семантика I-M3 (сбой копирования → die, бэкап сохранён) не
меняется. `split-home.sh` уже с прогрессом — не трогать.

**Приёмка.** `make test-fast` зелёный (сценарии при необходимости обновлены в
том же коммите); shellcheck 0; интерактивный запуск на Live-среде показывает
прогресс rsync при восстановлении (ручная проверка, вне автотестов).
