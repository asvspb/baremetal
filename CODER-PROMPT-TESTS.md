---

Ты — исполнитель задачи построения системы тестов для проекта deploy-baremetal
(Ventoy-флешки + автономный установщик Dual-Boot Ubuntu/Windows). Скрипты проекта
разрушающие (parted/mkfs/dd), поэтому безопасность тестов — абсолютный приоритет.

**Главный документ — `TEST-SPEC.md` в корне репозитория.** Читай его первым и
следуй ему; выполняй этапы §10 строго по порядку: T0 → T1 → T2 → T3 → T4 → T5
(этап T6/Pester — опциональный, пропусти, если Windows-машины нет). В коммите
решения этапа помечай соответствующую строку таблицы §10 значком ✅.

## Контекст (что уже есть)

- Git-репозиторий с историей задач; pre-commit hook запускает `check-files.sh`
  (проверка BOM/CRLF/`$var:` у ps1 и `bash -n` у sh) — держи его зелёным.
- Скрипты верхнего уровня уже имеют dry-run (`deploy.sh --full --dry-run`,
  `split-home.sh --dry-run`), `deploy.sh` имеет режимы `--prep-disk` и генерацию
  autounattend.xml с экранированием пароля.
- Прошлые классы ошибок, которые тесты обязаны ловить: дубль ps1, кодировка
  без BOM, `$var:` в строках ps1, молчаливый сбой бэкапа с потерей данных.

## Окружение (проверено)

- Linux, bash. **Установлены:** shellcheck, losetup, truncate, fakeroot,
  `/dev/loop-control` (loop-устройства доступны). **Не установлены:** bats,
  pwsh, xmllint — их ставит твой `tests/setup.sh` (этап T1).
- `sudo -n` работает без пароля — уровни L4/L5 можно запускать под root.
- Сеть может отсутствовать: если поставить pwsh не удалось — уровень L1 обязан
  выдавать SKIP (жёлтым), а не FAIL. Это штатная деградация по TEST-SPEC §12.

## Железные правила (нарушение = переделка)

1. **Тесты никогда не исполняют parted/mkfs/dd/mkswap на реальных дисках.**
   Допустимые цели: `/dev/loop*` (L4) и tmp-каталоги (L2/L3). Каждый тест L3/L4
   начинается с assert-проверки имени целевого устройства. Заглушка `dd` из
   `tests/stubs/` всегда возвращает ошибку.
2. **T0 (рефакторинг guard) не меняет поведение.** Порядок работы строго такой:
   сначала зафиксируй эталон `bash deploy.sh --full --dry-run` (под sudo) в
   `tests/fixtures/dry-run-prep.golden`, потом рефактори, потом сравни вывод —
   расхождение = провал T0. RAM-копия deploy.sh и загрузка deploy.conf обязаны
   работать как раньше.
3. `split-home.sh` и `make-boot-usb.ps1` НЕ редактировать (ps1 — вообще не
   трогать: это Windows-файл с BOM/CRLF; если тест требует изменений в нём —
   остановись и опиши ситуацию в итоговом сообщении).
4. Один коммит = один этап (или осмысленная часть этапа), сообщение вида
   `T2: unit tests for deploy.sh helpers`.
5. Заглушки обязаны соответствовать фактическим вызовам из кода: перед написанием
   stub сверь сигнатуру grep-ом по скрипту (контракты — TEST-SPEC §6).
6. Никаких изменений интерактивного UX и русских сообщений скриптов.

## Что построить (сводка по TEST-SPEC, детали — там)

- `tests/setup.sh` — bats-core/bats-support/bats-assert (клоны в `tests/.deps`,
  версии по коммиту, в .gitignore), pwsh, xmllint; idempotent.
- `tests/run-all.sh` + `Makefile` (`test-fast` без root: L0–L3; `test`: +L1+L5;
  `test-loop`: L4 с предупреждением). Ненулевой exit при любом провале, сводка
  в конце, timeout-обёртка на тесты с stdin (зависший read = провал).
- Bats-наборы по §7: юниты (iana_to_windows_tz, part_dev, verify_restored_tree),
  CLI-валидация, стаб-интеграция бэкапа (включая критические I-M3/I-M4: сбой
  копирования → флешка не тронута, сверка не сошлась → бэкап сохранён),
  generate_autounattend со спец-символьными паролями + xmllint, loop-сценарии
  L-T1..L-T3 с losetup и очисткой в trap, dry-run E2E против golden-файла,
  метатесты M-1/M-2, ps-парсинг P-1 + канарейка P-2.
- Pre-commit hook: после check-files.sh добавить быстрый уровень (`make test-fast`),
  сохранив прежнюю функциональность.
- README: раздел «Тестирование».

## Проверки в конце каждого этапа

```bash
make test-fast                 # зелёный, без root
sudo -n make test              # зелёный (L1 SKIP без pwsh — допустимо)
bash tests/run-all.sh fast     # та же логика напрямую
git status --short             # чисто (кроме запланированных артефактов)
```

## Определение готовности (DoD из TEST-SPEC §9)

1. `make test-fast` зелёный без root; `sudo make test` зелёный (или SKIP pwsh).
2. Критические тесты данных I-M3/I-M4 существуют; один раз проверь их остроту —
   временно «сломай» проверяемый код (например, верни `|| true` на копировании)
   и убедись, что тест краснеет; восстанови код. Результат зафиксируй в итоговом
   сообщении.
3. Метатесты M-1/M-2 зелёные; `shellcheck -S warning` = 0 на всех .sh (включая новые).
4. Три подряд прогона полного набора дают одинаковый результат.
5. `git log` читается как история этапов; TEST-SPEC §10 помечен ✅ по факту.
